## 1. 你必须先知道的硬性环境约束（踩过的坑）

这些是血泪教训，**不遵守必爆**：

- **XcodeGen** 在 `/usr/local/bin/xcodegen`（版本 2.46.0），项目文件由根目录 `project.yml` 生成，不是手写 `.xcodeproj`。**改了 project.yml 必须 `xcodegen generate`**。
- **所有 build/test 必须带 `ONLY_ACTIVE_ARCH=YES ARCHS=arm64`**，否则报 "built for incompatible target"（universal-arch 问题）。**不要用 M1 用户那套 `-destination 'generic'`**。
  - iOS 构建验证：
    ```
    xcodebuild -project FlashNote.xcodeproj -scheme FlashNote -sdk iphoneos CODE_SIGNING_ALLOWED=NO ONLY_ACTIVE_ARCH=YES ARCHS=arm64 build
    ```
  - macOS 测试验证：
    ```
    xcodebuild -project FlashNote.xcodeproj -scheme FlashNoteMac -destination 'platform=macOS' ONLY_ACTIVE_ARCH=YES ARCHS=arm64 test
    ```
- 当前 Xcode 26.6；iOS 26.5 模拟器运行时已装，但 xcodebuild 只能看到 macOS destination（看不到 iOS simulator）。**macOS 是真机测试载体**。启动 app 用 `open`，**不要直接跑二进制**（否则 TCC 权限责任归属到启动它的终端 app，引发隐私崩溃）。
- **物理 Info.plist** 在 `Resources/Info.plist`（用 `GENERATE_INFOPLIST_FILE` + `INFOPLIST_KEY_*` 生成出来的 plist 在 macOS 26.5 上不可读，会触发 TCC）。这个物理 plist **必须包含**以下 key（缺一个就 `__TCC_CRASHING_DUE_TO_PRIVACY_VIOLATION__` 崩溃）：
  - `NSMicrophoneUsageDescription`
  - `NSSpeechRecognitionUsageDescription`
  - `NSBluetoothAlwaysUsageDescription`
  - `NSBluetoothPeripheralUsageDescription`
- **核心框架是 static**（`MACH_O_TYPE: staticlib`）。**动态框架在启动时崩溃**（dyld 找不到 `FlashNoteCore.framework`）。别改成 dynamic。
- `FlashNoteCore` 集成方式：**两个 framework target**（`FlashNoteCore` iOS / `FlashNoteCoreMac` macOS，module 名都是 `FlashNoteCore`）。**不要**换成 XcodeGen 本地 Swift package（local-package 多平台路径有 bug）。
- 测试文件用条件导入：
  ```swift
  #if os(macOS)
  @testable import FlashNoteMac
  #else
  @testable import FlashNote
  #endif
  ```
- test target 需要 `GENERATE_INFOPLIST_FILE` + `TEST_HOST` + `BUNDLE_LOADER`；app target 需要 `ENABLE_TESTABILITY`（否则 `@testable` 失败）。
- 真机 BLE 测试：**macOS 系统设置 → 蓝牙里不会列出 CB08**（它是 BLE peripheral），只有 CoreBluetooth 扫描能找到，这是正常的，别当 bug。

## 4. BLE 协议（QS668/CB08）速查 —— 已实现并验证

### 4.1 GATT
- Service `0xAE20`
- `AE21`：写（`.withoutResponse`）——控制/下达命令
- `AE22`：通知 —— 控制/音频/列表/文件
- `AE23`：通知 —— 按键/录音状态（当前代码只订阅了 AE22；AE23 尚未使用）

### 4.2 帧格式
```
[0x5A][SEQ][CRC:2B LE][LEN:2B LE][DATA=TYPE+CMD+PARAMS]
```
- CRC-16/**XMODEM**：poly 0x1021, init 0, RefIn/RefOut=false, XorOut=0；CRC 输入 = LEN 原始 2 字节 + DATA（**不含** MAGIC/SEQ/CRC）。
- `LEN > 8192` 视为假帧头，跳一字节重同步。

### 4.3 命令类型（TYPE:CMD）
- TYPE 0 控制：3=电量, 4=电量应答, 10=版本, 11=版本应答, 12=授权码, 13=授权码应答
- TYPE 1 实时：0=开始, 1=音频码流, 2=停止, 3=暂停/继续, 4=状态
- TYPE 2 文件：0=列表请求, 1=列表数据, 2=导入请求, 3=导入开始（记录实际名）, 4=文件数据, 5=结束（0完成/1不存在/2offset错/3其他）, 7=中止, 18=列表完成
- TYPE 3 按键/录音：1=开始, 3=保存, 5/7=暂停/继续, 20=状态

### 4.4 文件列表条目
- 数据体：`count:4B BE` + N×`[time:4B BE + size:4B BE + name:20B]`（每次 28 字节/条）。
- **`size` 是压缩大小**（设备里存的 OPUS 大小），**不是**下载后的 WAV 大小。`name` 字段 20B 会被截断，且列表名常以 `.` 结尾、无扩展名。
- `CB08FileEntry.candidateNames` = 去掉末尾 `.` 和已知扩展名后的 base → `[base.wav, base.opus, 原始截断名]`。真实文件格式为 `.wav`。

### 4.5 已踩过并修掉的坑（重要，别回退）
1. **`frame.params` 用 `Data.dropFirst(2)` 而不是 slice**。之前返回 slice（startIndex≠0），下游 `subdata(in:)` 用共享索引空间读错 offset，导致文件列表名解析成 "Kxnote..."。现在 `params` 就是 `Data(data.dropFirst(2))`。
2. 文件名候选曾产出 "xx..wav"（双点），因为 name 末尾带 `.`。已 fix：先 strip 末尾 `.` + 已知扩展名。
3. 下载"卡死"：设备会**连续**发 CMD4 数据分片，但之前**日志里从未观察到 CMD5 结束帧**，导致永远等不到结束。已加 **6 秒空闲超时兜底**（收到数据后 6s 无新数据且无结束帧 → 视为完成）。
4. 下载慢的根因：`CB08Central` 里曾经**每帧打 os_log**（约 3.4 万帧，每帧一条），成为瓶颈。已移除每帧 log，只保留连接层 log。**别再加回每帧 log。**
5. 进度条不动：`DeviceTranscriptionService` 更新的 `progress` 和 `DeviceViewModel`/面板读的 `progress` 曾是两个对象。已通过 `onProgress` 回调接上。

## 5. BLE 下载链路现状（重点，几乎完成但卡在最后一步）

### 5.1 数据流
```
filesSection 点"下载转写" → vm.downloadAndTranscribe(file:) 
  → transcription.downloadAndTranscribe(file:title:) 
      → expectedSize = UInt32(time * 32000 + 44)   // WAV 估算
      → download(file:)                          // 候选名回退 base.wav→base.opus→原始名
          → downloadOne(name:)                   // withCheckedThrowingContinuation
              → device.requestImport(filename:name)  // 接 CMD4 分片 + CMD5 结束 / 6s 空闲超时
      → 写 audio/<uuid>.wav 
  → engine.transcribe(audioFileURL:) → Transcript
  → store.upsertRecording + upsertTranscript → return
```

### 5.2 `CB08Device` 下载回调
- `onDownloadData:(Data)->Void` —— 每收到一分片（CMD=4）
- `onDownloadComplete:(Data,String)->Void` —— 完整文件 + 实际名（CMD=5 且 code==0）
- `onDownloadCode:(UInt8)->Void` —— 结束码（CMD=5）

### 5.3 关键流程/顺序（不要弄乱）
`handleFile` 里：**CMD3**（导入开始）设置 `importingName`（真实文件名）；**CMD4** append 到 `downloadingBuffer` + 触发 `onDownloadData`；**CMD5** 先触发 `onDownloadCode`，若 code==0 且 `importingName != nil` 再触发 `onDownloadComplete(downloadingBuffer, importingName)`。

### 5.4 DeviceTranscriptionService 的候选名回退逻辑
```swift
for name in file.candidateNames {   // base.wav → base.opus → 原始截断名
    do { return try await downloadOne(name: name) }
    catch DeviceError.downloadCode(1) { /* 换下一个候选 */ }
    catch { throw error }            // code != 1 直接抛
}
```

### 5.5 6s 空闲超时兜底（防止永不结束）
```swift
func restartIdle() {
    idleTask?.cancel()
    idleTask = Task {
        try? await Task.sleep(nanoseconds: 6_000_000_000)
        guard !Task.isCancelled else { return }
        if !buffer.isEmpty { resumeIfNeeded(.success((buffer, name))) }
        else { resumeIfNeeded(.failure(DeviceError.downloadCode(1))) }
    }
}
```

## 7. 当前未完成 / 待办（按优先级）

### 🔴 P0 —— 下载"没成功、进度条不动"的最后诊断（就是现在卡的点）

**用户最新反馈**：点下载后进度条不动、且下载不成功。上面 P0 相关改动（onProgress 接线 + expectedSize WAV 估算）**已提交但没有经过真机验证**。这是接手后的**第一件事**。

建议排查顺序：
1. **确认进度条/状态已接到位**（上一步刚改）——
   - `DeviceViewModel.downloadAndTranscribe` 里 `self.transcription?.onProgress = { self.progress = $0; self.statusText = $1 }`（已加）。
   - 面板 `DevicePanelView.swift` line 125 `if vm.progress > 0 && vm.progress < 1 { ProgressView(value: vm.progress) }`。
2. **确认设备真的在发数据、且 CMD4 分片被接收**。因为移除了每帧 log，可临时加一个**非每帧**的最小 log（例如：下载开始时 1 条、每 1MB 1 条、结束 1 条），观察是否收到数据。
   - 若**完全收不到数据** → BLE 订阅/写通道问题，检查 `CB08Central.didDiscoverCharacteristicsFor`（需 AE21 写 + AE22 通知都拿到才 `isConnected=true`）。
   - 若**收到数据但进度不动** → 进度绑定/回调没到位（对上面的 1）。
   - 若**收到数据但一直不结束** → CMD5 没到，6s 空闲超时兜底是否生效（检查 `restartIdle` 有没有被每帧 `onDownloadData` 重置；如果设备持续发数据超过 6s，兜底永远不触发——需要一个"达到 expectedSize 就结束"的判据）。
   - **重要**：`expectedSize` 是 WAV 估算值 ≈5.5MB。但若设备实际传的是"压缩 OPUS"大小（347KB）就结束了，那么 `buffer.count` 永远到不了 5.5MB，进度走到 0.06 出头后**若 CMD5 没来会卡住**直到空闲超时。**这就是"进度条不动/不成功"最可能的根因之一**：进度分母（5.5MB）和实际传输量（347KB 压缩）不匹配。
3. **验证用 open 启动 app**，连接后点下载，观察日志/状态文本。

> **关键判断**：用户希望"下载快、5.5MB 缩小"。真正根解是 **OPUS 解码**（见 P1）。在 OPUS 解码落地前，下载 5.5MB WAV 是**硬件固件层面的慢**（每帧 160B × ~3.4 万帧），不是你代码慢，别把时间耗在"提速"上。

### 🟡 P1 —— OPUS 解码（Phase A Task 4，最大不确定项，被顺延）

- **为什么重要**：设备实时流是固定 **40B/包原始 OPUS**（Opus config 9，20ms，16kHz）；下载路径设备返回 WAV（可不用 OPUS，但 5.5MB 慢）。若 OPUS 解码做通，就能：
  1. 只下载 **347KB 压缩 OPUS** 而不是 5.5MB WAV（下载快十几倍，匹配声云速度）。
  2. 实时流 40B 包 → PCM → 喂流式 ASR（阿里云 Qwen-ASR-Realtime）。
- **Apple 无原生 OGG/Opus 解码**。方案三选一：
  - **a. SwiftPM C 目标打包 libopus**（`opus` + 桥接头）——最稳，但要网络拉取。
  - **b. AudioToolbox `AudioConverter`**（需验证是否支持该格式）。
  - **c. 参照厂商脚本**：40B 包 → 包装成 OggS → 用 `AVAudioFile`/`AudioFile` 读（若支持）。
- 先在某处验证可行的解码路径；若 libopus 不可拉取用 c 方案（包装 Ogg + 系统解码）。
- 参考 `github.com/lomehong/record`（含 Python 实现与 OPUS→OGG 包装脚本）。
- **注意**：之前 `git clone` 该 repo 时 **curl 28 连接超时**，V2 设计文档里写了"物流单号获取厂商资料页"，但那页可能已失效，优先用 `lomehong/record`。

- 真机验证需录音笔开电 + 声云 app 关闭。
