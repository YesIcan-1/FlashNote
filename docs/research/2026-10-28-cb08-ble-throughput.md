# CB08 蓝牙录音下载吞吐排查（2026-10-28）

## 同一录音的实机对照

测试文件：`note20260822-190246.opus`，347000 字节。Mac 与录音笔近距离连接，先用 NextProto 的 Bleak 客户端下载，再用 FlashNoteMac 下载；两次之间设备重新进入可连接状态。

| 客户端 | 耗时 | 有效吞吐 |
| --- | ---: | ---: |
| NextProto/Bleak 独立客户端 | 16.293813 秒 | 20.80 KiB/s |
| FlashNoteMac | 16.564228 秒 | 20.46 KiB/s |

两者相差 0.270415 秒（约 1.7%）。之前 FlashNoteMac 对同一文件的多次下载约为 17–20 秒。独立实现达到相近速度，说明 FlashNote 的文件写入、进度更新和帧解析不是主要限速点。

## 连接和收包证据

- macOS `bluetoothd` 在两次连接中都报告 `txPhy=2, rxPhy=2`（2M PHY）、收发 Data Length 251 字节、ATT MTU 527；FlashNote 的 `maximumWriteValueLength(.withoutResponse)` 是 512 字节。因此此时并非停留在默认 23 字节 MTU 或 1M PHY。
- FlashNote 收到 2169 个文件数据包，共 347000 字节；单包 120–160 字节，绝大多数为 160 字节。协议请求只发送一次，设备通过 AE22 Notify 主动推送数据，没有应用层逐包确认。
- 16.56 秒内，FlashNote 的 CoreBluetooth 通知分发及后续处理累计 约 0.15 秒；其中写文件、进度更新等下载回调累计 0.117 秒。纯 Swift 帧解析对同等数量和尺寸的合成数据重复基准测试约 3.85 毫秒/轮。
- 文件数据包到达间隔分布（2168 个间隔）：`<1ms 959`、`1–5ms 624`、`5–10ms 40`、`10–20ms 72`、`20–40ms 441`、`40–80ms 30`、`>=80ms 2`。呈现短时间成批到达，随后等待 20–40 毫秒的节奏。系统在断开时记录该连接间隔为 15ms，但仅凭应用层间隔不能进一步断言设备内部的具体调度原因。

## 判断和下一步

用户认为蓝牙理论速率应高于当前速度，这一点得到连接参数支持。当前约 20 KiB/s 的限制更可能发生在录音笔固件的文件读取/Notify 推送策略、每次发送的 160 字节协议块大小，或链路事件调度。没有外设固件计数器或空口抓包，暂不能把责任确定到某一项。Mac 应用无法通过公开 CoreBluetooth API 直接设置外设的连接间隔、每事件通知数或文件发送块大小。

若能修改录音笔固件，应记录每次文件读取、Notify 入队和发送时间，验证能否在已协商的 MTU/2M PHY 下发送更大的块或提高每连接事件的包数，再用同一 347000 字节文件复测。先保留现有 2-2 请求整帧单写和断点续传行为，避免破坏协议兼容性。
